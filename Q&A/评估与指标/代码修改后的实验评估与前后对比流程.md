## 建议总流程

保留修改前参照 → 明确改动与成功标准 → 检查计算和代码 → 短试跑 → 必要时同预算训练 → 同场景评估 → 分析策略与场景变化 → 输出前后对照报告。

将“改得正确”和“模型效果提高”分别判断。修正错误后分数降低，不自动表示修改失败；分数上涨也不能替代计算正确性验证。每种改动都留下验证记录，但检查深度随影响范围调整。

## 一、修改前先留下能复现的参照

每次实验使用独立编号，保存：

- 原代码与新代码的快照或版本标识；当前仓库没有 Git 元数据，可以先保存源码快照及校验值。
- 修改目的、涉及文件、预期改善的问题，以及明确保持不变的条件。
- 原权重、新权重、训练设置、网络参数量、动作与功率含义、环境和奖励版本。
- 完整场景数组：位置、需求、顺序、分组及资源预算。随机种子也要记录，但不能只保存种子，因为代码和依赖变化可能改变随机数的消耗及场景生成。
- 解释器、依赖版本、GPU/CPU、线程数、实际训练命令与随机种子。

历史结果保留原始数据，不覆盖。把“当前认可的参照版本”与“本次候选版本”明确对应起来，不凭文件名最新或某张图最好来挑参照。

## 二、先按改动类型确定对比方式

| 改动类型 | 主要检查 | 是否需要重训 |
| --- | --- | --- |
| 路径、日志、整理、保持数值含义的提速 | 同权重、同场景、必要时同动作序列，比较输出与中间计算；在相同硬件负载下比较耗时 | 一般不需要；若改到更新过程，应核对梯度或更新结果，并按影响增加短训练对照 |
| 指标统计或绘图修正 | 所有待比较模型采用同一正确口径，图由原始数据生成 | 通常只需重新评估；旧图保留为历史记录 |
| 奖励或学习公式 | 修改前后分别训练，其他条件对齐，比较实际服务结果、约束和学习过程 | 需要；不同奖励公式的回报数值不能直接比高低 |
| 功率、干扰等环境计算或动作规则 | 区分环境改动本身的影响、旧模型适应程度与重训收益 | 至少重评旧模型；需要报告适应新环境后的能力时再重训 |
| 网络结构或输入信息 | 固定环境和预算，记录参数量、计算量与实际输入变化 | 需要；不兼容的旧权重不强行转换成看似可比的旧模型 |

对环境修改，至少区分三组：

| 权重与环境 | 用途 |
| --- | --- |
| 原权重＋原环境 | 复现和保留历史结果 |
| 原权重＋修正环境 | 看原模型在修正规则下还能达到多少；仅在输入、动作含义兼容时直接执行 |
| 重训权重＋修正环境 | 看重新学习后的表现 |

如果同时修改环境和学习算法，还应加入“原算法在修正环境重新训练”的参照，再与“新算法在修正环境重新训练”比较。否则环境与算法带来的变化混在一起。

旧公式下的 95 分与修正公式下的 85 分，不能直接用来认定修改退步。正式算法排名应放在同一套已核清的环境中；旧错误环境的结果只能作历史诊断。

## 三、先检查计算，再跑完整实验

检查应针对本次修改及受影响范围：

- 环境变化：用能手算或明确判断的小场景检查功率总账、槽数、干扰对称性、终止和最终指标。
- 算法变化：确认实际参数更新被执行，数值有效、更新对象正确，而不只是成功完成前向计算。
- 路径或依赖变化：检查模块导入、输入输出位置及旧权重兼容性。
- 评价变化：检查原始数组、逐步日志与每回合总指标一致，缺少权重时停止而不是继续用随机模型。
- 运行少量完整回合检查输出、终止、保存重载和覆盖风险。正式训练前确认 DQN 解释器、CUDA 及项目导入条件。

针对性测试通过后再进入正式阶段。发现错误应保留失败原因，不通过删除低分或失败场景让检查通过。

## 四、把学习、日常比较和最终考核分开

建议三类场景：

1. **训练场景**：用于更新参数。
2. **日常比较场景**：用于开发时反复比较、观察中途表现及选择保存节点。可反复使用，但应承认开发过程已经参考过它们。
3. **最终考核场景**：方案和选择规则确定后用于最终报告，不用于不断挑版本或调参数。

正常需求、较高/较低需求、顺序变化、预算变化和地理变化都可以有对应的考核场景，具体取决于本次修改。压力场景与原场景保持配对，一次主要改变一个条件；排序试验若要单独看顺序，应保留波束身份和原分组。

若根据最终考核结果又调整代码，该批数据就已参与开发，不应继续称作从未使用的最终考核。应如实说明，并为后续最终结论补充新的独立场景。

## 五、训练按同一预算比较，并定期保存

- 算法比较优先对齐环境交互步数，即模型实际做了多少次分配，而不只对齐回合数。当前回合会因超功率提前结束，同样 4000 回合未必有相同交互量。
- 同时记录参数更新次数、实际回合数、训练时间；比较速度时记录设备、线程设置及 GPU 是否被其他任务占用。
- 保持其他训练条件一致，一次尽量围绕一个问题。必须一起修改时，把它们作为一个明确的方案整体报告；要分辨各自贡献则做分开对照。
- 正式结果以多个独立训练种子为起点，例如先做 3 次；3 次不保证证据充分，波动大时应增加。展示每个种子的成绩，不能只报最好一次。
- 按预定间隔在日常比较场景上评价，保存固定训练预算结束的模型、日常比较规则选中的最好模型，以及继续训练所需的断点。
- 预先确定以哪个模型作主结果。若研究相同预算下的学习效果，可以最终模型为主、最好模型为补充；不能看最终考核结果再挑保存节点。
- 中途评估使用独立环境与随机数状态，不能因多测一次就改变后续训练的场景和采样过程。

正式训练和长评估按当前已有协作约定由子 agent 在 DQN 环境后台执行，主任务负责方案和结果讨论。单 GPU 的排队与并行方式需记录；不能因并发占用而把耗时差异误当算法速度差异。

## 六、每次评价使用同一组核心指标

| 方面 | 建议必报内容 | 目的 |
| --- | --- | --- |
| 约束与完成情况 | 超功率回合比例、完整分配比例、提前终止位置、频率越界和冲突 | 先确认是否完成了规定任务 |
| 服务表现 | 全部波束的最终满意度、各场景新旧差值、波动、吞吐量；SGM 单独列出 | 区分真正服务改善和指标名称变化 |
| 功率和频谱 | 总功率、请求槽数、实际成功槽数、无效分配 | 确认高分付出的资源代价 |
| 学习过程 | 同预算下的考核曲线、回合与更新次数、同奖励版本的训练回报 | 判断学习速度和稳定性 |
| 实际开销 | 训练耗时、单次分配或完整场景推理耗时、参数量和显存 | 判断改善是否值得新增成本 |

最终满意度按所有波束计算，包含后续干扰损失，未服务波束记零。超限回合应保留，并与合规率同时展示；不能只平均成功回合来隐藏失败。指标公式、单位、约束是否满足及必要数值容差应事先写明。

在相同场景上比较“新结果减旧结果”，报告平均变化、各训练种子表现、多少场景改善/下降及不确定范围。轻微上涨且反复训练不稳定时，应标为证据不足，而不是直接认定改进有效。

## 七、日志分析要说明模型怎样取得成绩

延续已有审计脚本，至少分析：

- 功率与槽数的选择分布，是固定偏好还是随状态改变。
- 不同需求得到多少槽、多少功率；是否只是分配阶段与需求排序同时变化造成的表面关联。
- 前后阶段的功率消耗，预算紧张时是否减少消耗。
- 频率起点是否被占用、请求是否越界、请求与实际分配相差多少。
- 最终高分是否依赖排序、某类地理条件、某个负载或环境自动裁剪。

把每项判断连接到具体日志或对照，而不只描述一条更高的曲线。缺历史训练数据时，不因一次压力测试下降就直接认定过拟合。

## 八、按修改影响控制实验规模

以下是讨论用的起步档位，不是已确定的统一预算：

| 阶段 | 示例规模 | 能支持的结论 |
| --- | --- | --- |
| 快速检查 | 针对性检查＋5～10 个固定场景；涉及更新时检查实际更新 | 代码与指标是否能正常、正确运行 |
| 候选方案筛选 | 1 个训练种子、预定短训练预算，约 100 个日常比较场景 | 是否有值得继续检验的趋势，不能当作最终稳定排名 |
| 正式比较 | 从 3 个训练种子起步、共同训练预算；每个模型约 100 个最终场景，相关压力条件各约 20 个配对场景 | 前后效果、约束与场景变化的较完整比较，视波动决定是否增加 |

原有待确认的 18 次训练、40 万步等具体计划仍是独立事项，本次流程讨论不构成对该计划的确认或执行授权。

## 九、固定交付一份前后对照报告

建议报告固定包含：

1. 这次改什么、预期解决什么、哪些条件保持不变。
2. 旧/新版本、权重、运行环境、场景与训练预算。
3. 检查是否通过，以及未通过事项。
4. 旧版、新版、差值的主指标表，约束结果必须与满意度同列。
5. 同预算训练曲线、场景对比、策略偏好和开销变化。
6. 每个训练种子的结果、原始日志、配置与复现命令。
7. 明确结论：计算修正得到验证；效果提高；效果相当但更快；效果下降；或证据不足。

正确的计算修复不能仅因分数下降而撤回。算法候选若未带来可靠收益，可保留为实验记录而不替换参照版本。图表由原始数据生成，不手工替换点值。

产物可集中在 `outputs/experiments/<实验编号>/`，按旧版、新版、训练种子分别保存配置、日志、指标、图表和报告；模型依项目规则放入 `models/runs/` 的对应实验目录。继续使用 `paths.py` 与 `SATELLITE_RL_OUTPUT_ROOT` 隔离输出，具体目录约定待实现时统一。
