# 训练场景与随机需求生成

回答日期：2026-09-27。适用实验：已完成的 `workbench_mask_20260925` 两组旧奖励、原T-SAC13令牌Transformer、掩码关闭/开启对照。

## 问题

当前训练的数据是怎样的，是不是固定的加上一些随机扰动？

## 结论

**可以概括为：固定100个城市的位置与资源条件，每回合重新随机生成业务需求；需求本身包含“重新抽取档位”和“叠加小扰动”两层变化。** 因此，固定的是地理位置集合与生成规则，业务需求会有较大变化。当前数据由仿真程序生成，城市表提供坐标，未导入实测业务流量序列。

| 项目 | 本轮实际做法 |
| --- | --- |
| 地理位置 | `data/cities_china.csv` 恰好100行、100个不同坐标，每回合不放回抽取100行，所以仍是同一组城市；坐标没有另加扰动 |
| 业务需求 | 每回合对100束重新抽取100、200、…、1000 Mbit/s的基础档位，各档等概率，再叠加标准差20 Mbit/s的高斯扰动并取整 |
| 分配顺序 | 按本回合需求从大到小排列；先抽城市的顺序与排序后的城市顺序会变化，按需求优先的规则保持不变 |
| 频率组 | 按处理序号对8取余，循环分组；规则固定，但同一城市在不同回合的序号和组别可能不同 |
| 天线增益与噪声 | 发射/接收最大增益分别固定50/40，噪声温度固定290 K；距离按城市位置和固定卫星位置计算 |
| 资源条件 | 100束、8组频率资源、每组100槽，总功率预算3000 W，功率档位5、10、…、50 W |
| 回合内变化 | 本回合位置和需求在100次顺序分配中保持固定；频率占用、剩余功率和干扰随分配动作变化 |

代码中有均值200 Mbit/s、标准差50 Mbit/s等早期参数定义，但当前需求生成没有使用它们；解释应以正在执行的 `np.random.choice(valid_rates) + rate_noise` 为准。生成负需求时旧代码将其改为100 Mbit/s，工作台还要求需求严格为正。基础档位范围并非加扰动后的硬范围，最终需求可以略低于100或略高于1000 Mbit/s。

## 需求生成公式

对回合 $e$ 中的波束 $i$，排序前生成：

$$
D_i^{(e)}=\left[b_i^{(e)}+\operatorname{round}(\epsilon_i^{(e)})\right]\ \mathrm{Mbit/s},
\qquad b_i^{(e)}\sim\mathrm{Uniform}\{100,200,\ldots,1000\},
\quad \epsilon_i^{(e)}\sim\mathcal N(0,20^2).
$$

随后执行上述负值保护及需求降序排列。这里的20是标准差，不是最大扰动限制。例如同一城市本回合可能抽到300 Mbit/s附近，下一回合可能抽到800 Mbit/s附近；它并没有一个在所有回合都固定的基础需求。需求不按城市人口或城市大小分配，也没有当前回合对上一回合的时间连续性约束。

## 训练、验证和最终考核怎样组织

- **训练：**每回合重新生成一份完整场景，一回合顺序分配100束。本轮每组4000回合、40万交互步；场景种子按 `51001 + 100000 + episode` 生成，回合从0开始，范围151001–155000。固定训练种子是为了复现相同的一系列场景，并不是4000回合使用同一份需求。实际数组保存在任务的 `scenes/train/scene_*.npz`。
- **对照：**两组采用相同场景种子和生成规则，掩码改变的是动作及后续资源状态。对照时需比较原始场景数组或其校验值，不能只依赖“种子相同”。
- **验证：**20个固定场景274000–274019，在每1万步重复评价，每场景3次随机动作；同一场景的数据固定，动作采样与场景生成是两种随机性。
- **最终考核：**100个场景275000–275099，每模型每场景3次随机动作。使用相同城市库和需求生成规则、不同于训练的场景种子；这是新的需求与城市排序组合，并不是换一套覆盖位置。

## 这意味着什么

当前实验主要检验**同一组地理位置、固定资源条件下，面对不同业务需求和处理顺序的分配能力**。它尚未验证城市范围改变、需求分布改变、热点集中或连续时间流量变化时的表现。当前“随机场景”应按这个范围理解，不能直接等同于任意真实场景。

## 追问：如何扩大训练场景并衔接第一阶段

回答日期：2026-09-28。用户关注固定地理和固定需求分布带来的泛化限制，要求下一步方案。

**建议采用“用户/航空器业务分布 → 波束覆盖方案 → 每束汇总需求 → 频率槽与功率分配”的数据流程。** 第一版固定100束及资源预算，改变合法波束布局、需求总量、热点位置/范围/强度和空间相关性；一回合内保持场景不变。随后接入第一阶段实际输出的波束指向、宽度和覆盖归属，再研究连续时间重配置。

开题报告提及ADS-B航空数据，因此优先核对该数据资产，纳入航路、枢纽及不同时刻航空器分布。仓库当前仅见城市表，未见ADS-B文件。航空器轨迹不是Mbit/s业务测量，需明确每架航空器的业务模型并按覆盖归属汇总，重叠覆盖不能重复计数。真实位置加假设需求仍应标为合成业务场景。

仅扩大坐标扰动和需求噪声不足以覆盖这些变化；现有结果也尚不足以定量断言新地理下的泛化有多差。204维有本束位置和当前干扰，但没有完整未来需求/位置。新增全局或逐束输入属于另一项需要配套验证的变更；数据对照两组必须用相同输入/网络，不能把新输入带来的改善全归因于数据。

工作台已支持100束CSV/NPZ导入；训练循环固定场景文件，并不会自动重新抽需求。内置验证/终点评价仍生成原100城市场景，因此方案必须补齐共同验证/考核入口。按日期、区域和轨迹/场景家族先切分，再生成扰动与覆盖方案，分别评价新地理、新需求及联合变化，并保留原范围考核。报告全部目标束终态需求满足率、SGM、基本服务、资源与约束；第一/二阶段联合评价还包括未覆盖需求。

建议先比较原数据和多场景数据两组，候选seed51001、各40万步；奖励和联合掩码固定。若改输入或环境，原数据参照也需同条件重训；G01旧权重只在兼容条件下补充重评。若要区分地理和需求贡献，再另行补两组单因素对照。不增加训练种子，不将新场景分数与历史分数直接排名。

完整字段、生成建议、分阶段预算、代码依据及数据来源见[训练场景泛化与第一阶段衔接方案](../../docs/方案/04_训练场景泛化与第一阶段衔接方案.md)。**本次仅给方案并归档；尚未实施或训练，效果待验证。**

## 追问：可用公开数据集及缺数据时的生成方法

回答日期：2026-09-28。用户要求沿“开源可用数据集”和“没有数据时如何生成更贴近真实业务、泛化更好的训练数据”两条线深入调研。

**结论：有可用原料，推荐组合使用；尚未找到能直接替换当前训练输入的长期实测航空/卫星通信需求集。** 航空主线优先已有ADS-B资产或ADSB.lol公开轨迹；WorldPop可提供地面人口分布；Telecom Italia Milan/Trentino能提供真实时空活动形状，但Internet activity不是Mbps。卫星Traffic Simulator公开包有用户位置和Mbps需求，不过属于一天的仿真样例，未见明确LICENSE；6G-NTN公开海事包是船舶数量，不是通信速率。公开下载、研究使用条件、开放许可在调研表中分别说明。

本轮实际匿名下载并读取两份小型研究包：71束样例24份MAT，四列为束号/纬度/经度/需求；6G-NTN船舶栅格336份MAT，168个小时坐标与数量成对保存。合计约2.54 MB，仅用于文件含义核验，未导入工作台或用于训练。当前卫星经度固定122.2°E，欧洲样例不能不核对可见性和覆盖条件就直接导入；平移后只能称合成场景。

缺数据时先做可解释生成器：用户/航空器位置与轨迹 → 接入人数与业务会话 → 时空相关请求量 → 覆盖归属 → 每束需求。需求应具备不同业务类别、日内变化、热点/航路、ON/OFF会话和局部突发；变化场景家族及其参数，不能只增大独立噪声或改成一种固定对数正态分布。若采用请求字节，按`8×字节/(时间窗秒数×10^6)`转换为Mbit/s；不能用已实现吞吐替代未受限需求。

评价先按区域、日期、轨迹和场景家族切分，再做增强；另保留未参与拟合的真实位置/活动驱动或不同机制生成的场景。用需求分位数、集中程度、空间/时间相关、突发持续时间等核查合理性，并做共同场景的模型服务与约束比较。缺少实测请求时只能证明在明确假设范围内的泛化改善，不能保证真实部署表现。

完整来源、许可证/访问条件、实测与仿真的区分、小样例检查记录和生成方法见[调研报告](../../docs/资料/03_公开数据集与合成业务场景调研.md)。没有提交外部申请、修改源码或启动训练；数据接入与学习效果均待后续验证。
