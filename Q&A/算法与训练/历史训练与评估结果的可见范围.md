## 追问：五种 SAC 并行比较，节省时间应跑多少回合

回答日期：2026-09-24。

### 问题

希望同时运行新增的 MLP/CNN 匹配规模版、对应的原 MLP/CNN 版，以及 Transformer SAC。为了节省时间，跑多少回合比较合适，能够看到明显的对比结果？

### 建议预算

建议第一轮五种模型统一使用 **2000 回合、各 1 个预先确定的训练种子**，用于探索趋势和发现较大的性能差异；不保证一定产生显著差异，也不将单种子排名当作论文最终结论。以下是一次连续训练中的观察节点，不是每到一个节点都从头重训：

| 节点 | 建议用途 |
| --- | --- |
| 约 500 回合 | 检查学习是否启动、数值与资源使用是否正常，不用于认定最终优劣。 |
| 约 1000 回合 | 比较早期学习速度，观察原 CNN 等较早趋稳配置。 |
| 约 2000 回合 | 第一轮主要比较节点；历史图中 T-SAC 大致趋稳，但原 MLP 及新增变体仍可能继续改善。 |
| 约 3000 回合 | 若 2000 回合附近仍明显提升或排名不稳定，再安排共同的更长预算比较。 |

2000 回合是节省时间与观察阶段性表现之间的折中，不是证明所有配置已经收敛。历史 MLP-SAC 图约在 2000–2500 回合进入平台，两个新变体没有完整历史曲线，不能预先指定它们的收敛轮次。3000 回合也不构成普适收敛保证。

若有模型补跑到 3000，应分别展示所有模型共有的 2000 回合结果，以及具有可比训练预算的延长实验。不要把一个模型的 3000 回合与另一个的 1000 回合作为等训练预算结果。论文最终实验应在确定预算后使用多个独立训练种子；例如从 3 个种子起步，并根据观察到的方差决定是否增加，这不是“3 个就保证充分”的标准。

### 比仅比较回合数更严格的控制

当前每回合最多分配 100 个波束，也可能提前终止。2000 回合最多约 20 万次环境交互，并不保证五种模型获得完全相同的交互数。若重点比较样本效率，应优先设置相同环境交互步预算，例如每种 20 万步，并同时记录实际回合数与梯度更新次数；若重点比较时间效率，则另报告实际墙钟时间。

建议五个配置均从随机初始化开始，并明确设置 Python、NumPy、PyTorch 的种子。使用相同预设的训练种子编号有助于复现，但不同架构消耗随机数的方式不同，因此还需要独立生成同一组固定评估场景。

可在每 200 回合左右对固定的独立评估场景进行评估并保存原始结果，例如 20 个预先选定的场景。比较回报、终态总体满足率、总功率/超限情况，并记录耗时。实际执行应明确策略是随机采样还是确定性动作选择；未分配波束的满意度按统一定义处理。观察训练曲线时可用相同的 100 回合滑动窗口，但要保留原始数据，窗口参数不能为某个模型单独挑选。

### 当前计算资源及并行建议

只读检查得到当前机器与训练环境：

**检查范围补充：** 本节最初检查的是默认 `C:/Users/Admin/anaconda3/python.exe`，不是用户指定的 `DQN` 环境。随后已单独检查 DQN 与实际 GPU，结果见文末；CPU 版 PyTorch 不代表机器没有独立显卡。

- CPU：Intel Core i7-14700KF，20 个物理核心、28 个逻辑处理器。
- 内存：约 31.9 GiB。

- 当前单进程 `torch.get_num_threads()` 为 20，inter-op 线程设置为 28。五个进程直接按默认设置运行，会有明显的 CPU 资源过度竞争风险，不能假定比串行快五倍。

[PyTorch 2.3 多进程文档](https://docs.pytorch.org/docs/2.3/notes/multiprocessing.html#avoid-cpu-oversubscription) 说明了多进程线程过度分配导致资源竞争的问题，并建议按可用 CPU 数和进程数约束每进程线程数。本次没有更改线程设置，也没有据此声称已经测得运行加速。

原三种 SAC 入口仍共用默认指标和图表目录，五任务并行时应给每次运行设置独立 `experiment_name` 或输出根目录，避免同一分钟保存时发生文件覆盖。新增 matched 入口已有各自名称，原三个入口也应为这次比较配置独立目录。

### 尚待确认与当前状态

没有进行吞吐基准测量，因此目前不能可靠承诺五组实验需要多少小时。应测量经验池超过 2000 步、实际开始梯度更新之后的速度，而不是用前几个尚未更新的回合外推总训练时间。

此前 CPU 判断来自默认 Python 环境，未检查 DQN，因此不能直接套用到用户通常使用的环境。本次通过 `conda run -n DQN` 单独执行检查，确认实际解释器和 torch 模块都来自 DQN：

因此，**当前 DQN 环境中的 PyTorch 确实是 CPU 构建，不能使用 CUDA 训练**。版本字符串没有 `+cpu` 后缀并不代表它一定支持 CUDA；这里同时核对了构建信息及包来源。

### 为什么看起来装过 CUDA，实际却不能用

Conda 包列表同时存在：

- `cuda-runtime 12.4.0`；
- `pytorch-cuda 12.4`；
- 但实际 `pytorch 2.3.1` 的构建为 `py3.8_cpu_0`；
- `pytorch-mutex` 为 `cpu`，torchaudio 和 torchvision 也为 CPU 构建。

这说明 CUDA 运行时/元包存在，但实际使用的 PyTorch 仍是 CPU 版本。仅执行 `conda activate DQN` 不会把 CPU 构建转换成 CUDA 构建。没有从这些信息推断用户之前如何安装，也没有认定显卡或驱动损坏。

### 机器实际具有 GPU

`nvidia-smi` 能正常识别 **NVIDIA GeForce RTX 4070 SUPER**，总显存约 **12 GB（12282 MiB）**，驱动版本 591.86。GPU 存在与当前 PyTorch 支持 GPU 是两个独立检查项。本次采样时显存已有部分占用，因此也不能把整卡总显存当作训练可用的空闲显存。

后续若为 DQN 配置正确的 CUDA 版 PyTorch，需重新验证可用性、一次实际 GPU 运算和训练吞吐，再决定五任务的 GPU 并发数；此前每进程约 4 个 CPU 线程只是 CPU 运行方案，不应机械套用到 GPU 训练。

### 额外的项目兼容性检查

DQN 当前尚无法定位 `satellite_rl` 包；并且它使用 Python 3.8.19，而项目 `pyproject.toml` 当前声明 `requires-python = ">=3.10"`。这意味着迁移后的项目不能直接按现有声明在该环境完成正常安装。此处只指出安装元数据与环境版本不一致，尚未完成在 Python 3.8 下逐项验证源码兼容性，不能据此声称全部算法都不支持 Python 3.8。
