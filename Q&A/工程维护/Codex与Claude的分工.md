# Codex与Claude的分工

来源：cc

## 2026-10-18 问题

Codex负责实现、Claude负责出报告，这样分工是否合理？

## 结论

**方向合理，但"Claude只出报告"不够。** S1-FIX里真正决定结果对错的，是设计和"在真实数据上验收代码"这两步；如果Claude只在最后写报告，那一轮的结论会是错的。建议的分工是：Claude负责设计、实现说明、上机前用真实数据验收、分析与报告；Codex负责写代码、单元测试和按修订说明改代码；只有几行的小修正由Claude直接改。

## S1-FIX的实际情况

| 环节 | 谁做 | 情况 |
| --- | --- | --- |
| 写代码 | Codex | 25分钟写出约2500行，28项测试全过，没有冗余设计 |
| 发现问题 | Claude在远端用真实场景试跑 | 6个问题，Codex自己的测试一个都没抓到 |
| 设计缺陷修正 | Codex按Claude的修订说明改 | 3轮，每轮25—40分钟；另有1轮Codex执行工具卡死，白等约25分钟 |
| 小修正 | Claude直接改 | 数值容差、PPO小批次、动态束数、时间上限等，每处几分钟 |
| 运行、分析、出图、报告 | Claude | 发现PPO只学到固定动作，补跑固定规则对照后才定论 |

漏掉会让结论作废的问题有三个：骨架在200束预算下只用了33束；PPO每次更新只走4步梯度、几乎不学；修补算子在预算用满时几乎每帧失败，所有动态策略的结果都一样。三者单元测试都过了，只有在真实数据上看结果才看得出来。

## 这样分的道理

- **Codex适合写代码。** 快、量大、按规格实现得准，这次也守住了"不做防御性编程"的要求。
- **设计者必须验收。** 规格里的缺陷（例如骨架问题，根源在Claude写的规格）只有提出设计的一方最容易看出"结果不对劲"。
- **报告者必须碰原始数据。** 报告的价值在于结论可信，而结论可信要求写报告的人亲自核过数据、必要时补跑对照。
- **小改动不值得来回交接。** 一轮交接约半小时，几行的修正直接改更快。
- **报告由Claude写**是用户10月17日的要求，原因是此前Codex的报告难读；这一点不变。

## 需要注意的

- 两边不要同时改同一个文件；Claude直接改的部分在提交说明里写清楚，报告附录注明哪些是谁改的（S1-FIX报告附录B已这样做）。
- 实验由谁上机都可以（W31、W32由Codex跑，S1-FIX由Claude跑），关键是写报告的一方核过原始数据。
