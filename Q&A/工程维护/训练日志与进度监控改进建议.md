## 当前实现的具体不足

1. **日志可能覆盖。** SAC 用分钟级文件名，构造器以 `w` 写表头。同一输出根下，同一分钟创建同种 agent 会覆盖日志；模型文件也用分钟时间戳。依据：[日志创建](/D:/paper/src/satellite_rl/agents/sac_transformer.py:215)、[模型命名](/D:/paper/src/satellite_rl/agents/sac_transformer.py:449)。
2. **写盘前已丢失精度。** 满意度、增量、SGM 等先格式化为两位小数。比如增量 0.996 会写成 1.00，但当前奖励仍走“小于 1”的分支，难以复核原因。原始记录应保留精度，只格式化显示。依据：[log_step](/D:/paper/src/satellite_rl/agents/sac_transformer.py:248)。
3. **SAC 学习内部不可见。** loss、alpha、熵、Q 和 TD 目标没有返回或持久保存；缺少总交互步、更新数、阶段和耗时，前 2000 条经验尚未学习时尤其容易误判。依据：[update](/D:/paper/src/satellite_rl/agents/sac_transformer.py:363)、[更新门槛](/D:/paper/src/satellite_rl/training/sac_runner.py:198)。DQN 已显示 loss/epsilon/回放量，PPO 已显示 Actor/Critic loss，不能泛称全部算法都没有 loss；主要缺少统一、可关联的持久记录。
4. **保存过晚。** SAC 先调用两个含 `plt.show()` 的绘图函数，再保存 npz 和模型；交互后端可能在图窗处等待。中途失败缺少专门落盘处理。依据：[训练结尾](/D:/paper/src/satellite_rl/training/sac_runner.py:221)、[show](/D:/paper/src/satellite_rl/training/sac_runner.py:46)。
5. **full_model 不等于完整续训断点。** 当前主要保存五网络，没有温度、优化器、回放、RNG、步数和环境进度。依据：[保存内容](/D:/paper/src/satellite_rl/agents/sac_transformer.py:457)。

## 建议一：实时进度摘要

终端与 `status.json` 共用同一状态源，每 1–2 秒刷新，不每步刷屏。显示 run_id、模型/版本/种子、设备、PID、开始时间；当前阶段（排队、预热、训练、验证、保存、完成、失败、中断）；交互步/预算、实际更新数、回合数、回放量；窗口 steps/s、updates/s、耗时与 ETA；最近验证分数、checkpoint 和告警数量。

最后心跳与最后进度变化分别记录，区分“进程还在”和“确实在推进”。ETA 按当前阶段估计，不能用预热速度外推参数更新阶段。后台子 agent 多作业可以从状态文件汇成总表。

界面示意，非真实运行数据：

```text
CNN-matched | seed=... | TRAINING | step=.../... | updates=...
速度=...步/s | 已用=... | ETA=... | 回放=... | 最近进度=...秒前
验证终态SI=... | alpha=... | entropy=.../目标... | checkpoint=...
```

## 建议二：记录分层，字段可以相互关联

| 记录 | 内容 | 建议频率 |
| --- | --- | --- |
| manifest/config | Git 提交、未提交代码快照/哈希、实际配置、设备版本、参数量、随机源、场景与校验值 | 启动；恢复时追加来源 |
| updates | Actor/Q1/Q2/alpha loss，alpha，三个头熵及总熵/目标，Q与TD目标范围、TD误差 | 每 100–500 次更新汇总 |
| episodes | 回报、最终 SI/SGM/吞吐、总功率、超限、已服务/总波束、零槽/裁剪比例、终止原因、耗时 | 每回合 |
| evaluations | 固定场景终态指标、场景/动作种子、模型模式、对应 checkpoint 与训练步 | 预定验证点 |
| traces | 请求动作、实际分配、预算前后、需求位置、奖励及组成 | 调试回合或配置为全量 |
| events | 启动/恢复、阶段变化、存盘、告警、异常和 traceback | 事件发生时 |

共同关联键为 `run_id / scene_id / episode / env_step / update_step`，明确单位。经纬度分列，需求和速率用数值列，不写成 NumPy 数组字符串。请求动作在 `env.step()` 可能原地裁剪前复制。原始浮点数保留精度，界面再四舍五入；如果 traces 采用采样，必须注明采样规则。

当时满足率用于行为追踪；最终成绩用全部目标波束的终态速率，未服务束补零。SI、SGM 分开，`si_sum / si_mean / beam_count` 明确区分；训练回报与独立验证成绩分开记录。

## 建议三：可选 TensorBoard 曲线

先用 JSON/CSV 保留事实数据，再通过 TensorBoard 查看跨模型、跨种子曲线。`SummaryWriter` 支持标量、直方图及带队列的异步写盘，见 [官方接口文档](https://docs.pytorch.org/docs/2.14/tensorboard.html)。本机 PyTorch 2.3.1 的 writer 源码也有 `max_queue`、`flush_secs` 和异步写盘实现。

推荐分组：训练/验证效果，alpha与动作熵，功率/槽数/裁剪分布，loss/Q/TD误差，阶段耗时与吞吐、GPU allocated/reserved 显存。梯度范数和直方图低频采样，不每步输出大张量。**DQN 当前未安装 tensorboard，采用时需加这一可选依赖；本次未安装。**

## 建议四：告警附带复现现场

NaN/Inf、非法概率或关键状态损坏应记录错误、尽力保存现场并停止失败作业；不要用坏参数覆盖最后正常 checkpoint。长时间无推进、熵长期过低、固定最高功率/槽数、零槽或超限率升高、Q/TD误差持续扩大、固定验证集连续退步等应提示检查，而不是把单次 loss 波动判为失败。

故障包关联最近正常 checkpoint、实际场景/步骤、输入、请求/实际动作、相关 batch 或采样索引与 replay、随机状态、近期指标和 traceback。保留最近几十步的环形记录，异常时落盘；严重 CUDA 错误可能使现场保存失败，所以正常周期断点不可省略。

监控只报告事实，不自动修改学习率、裁剪梯度、修复目标熵或改变动作分布。

## 建议五：可靠落盘与断点

每次运行使用时间、模型、种子与唯一后缀组成的 run_id，避免分钟级名称冲突。按项目路径约定保存：

```text
outputs/experiments/<run_id>/
  manifest.json  status.json
  updates.csv  episodes.csv  evaluations.csv
  events.jsonl  traces/  tensorboard/
models/runs/<run_id>/
  latest.pt  best.pt  final.pt
```

`status.json` 写临时文件完成后原子替换；先保存模型、指标和状态，再生成非阻塞图片。`best` 只由验证规则选择，最终考核不用来挑 checkpoint。

PyTorch [续训文档](https://docs.pytorch.org/tutorials/beginner/saving_loading_models.html#saving-loading-a-general-checkpoint-for-inference-and-or-resuming-training)明确区分推理权重与包含优化器等状态的训练断点。本项目精确续训还需要 alpha、replay/指针、RNG、计数、场景和环境进度。可先支持回合边界恢复，再扩展任意步恢复，并明确支持范围。后台保存前要复制一致快照；把仍会变化的 state_dict 引用交给线程，不保证存档一致。

## 建议六：保持算法框架和性能

- 在 `training/` 增加统一记录器；agent 提供本次更新已有的 detached 诊断值，保持算法模块不依赖 training/env 的边界。
- 不为日志额外做 Actor/Critic 前向，避免增加耗时或改变 Dropout 随机流。
- GPU 标量低频打包后一次取回；异步写盘不能抵消逐个 `.item()` 的同步成本。
- 文件保持打开并缓冲，按秒/批次 flush，结束和异常时收尾。有界后台队列需明确背压与写盘错误处理，关键结果不能静默丢弃。
- 常规吞吐用窗口墙钟时间；精细 GPU 计时只在诊断窗口使用 events/同步，避免每步增加同步。
- 按同输入/RNG的启用、关闭记录对照验证行为和开销；日志不应改变采样、模型模式或学习过程。

## 推荐顺序及未完成事项

先做唯一 run_id、manifest/status、回合/学习/事件记录、非阻塞进度显示、异常记录及先保存后绘图；再接 TensorBoard、低频策略/梯度诊断和有明确恢复边界的周期 checkpoint。可将其纳入下一版训练前准备方案。

实施时遵循项目改动评估技能：检查并发不覆盖、原始精度和单位、异常 flush、状态文件完整性、恢复能力，以及前后数值/RNG一致性和耗时。目前均为建议，尚未实施。
