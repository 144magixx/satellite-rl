# 207维全局信息消融与稳定性验证方案

日期：2026-10-01。提案P06。**仅方案，未实现新开关、未创建任务、未启动训练或评价。** 本方案基于已完成的G09；G09结果和暂停的定时跟进保持原状，不恢复P05的新奖励计划。

## 1. 下一轮要回答什么

推荐以207维为参照，做“每次去掉一项全局信息”的四组对照，检验平均需求、处理进度和剩余需求各自在另外两项保留时的作用。各组继续使用旧奖励、关闭dropout、每轮打乱场景，按真实维数输入，不补零。

本轮重点从“状态加得越多是否越好”转为“少量全局信息中，哪些帮助模型兼顾当前波束与后面的波束”。同时检查固定验证回报是否改善后进入平台，以及少数波束服务不足的问题。不能承诺原始训练回报逐回合上升。

## 3. 三项新增信息的实际含义

设当前准备分配的是第i束，i从0开始；总共100束，需求单位为bit/s。

| 字段 | 当前输入定义 | 可能的作用，尚待消融验证 |
| --- | --- | --- |
| 平均需求 | 全100束需求均值 ÷ 6e8 | 告诉模型当前场景总体需求尺度；平均需求也参与旧奖励中SGM的计算 |
| 处理进度 | i ÷ 100 | 告诉模型已处理多少束，剩余功率还需支持多少束 |
| 剩余需求 | 第i束至最后一束需求之和 ÷ (100×6e8) | 告诉模型当前及后续待分配波束的总需求 |

“剩余需求”包含当前束；它不是扣除已供容量后的全场景欠供量。处理顺序仍按场景内需求降序，打乱的是场景出现顺序。

三项存在关联：在第0束，归一化的平均需求与剩余需求恰好相等；之后它们与处理进度、需求排序共同变化。因此，删除某项后不变差，只能说它在另外两项存在时未显示额外收益，不能证明它永远无用。

尤其要保留环境计算平均需求的逻辑。删除平均需求观测时，只从策略、双价值网络及目标网络的输入中移除该字段；奖励、SGM、掩码、场景需求和评价公式全部保持原值。否则就同时改变了状态和奖励。

代码依据：[状态布局](../../../src/satellite_rl/state_layouts.py)、[状态构造](../../../src/satellite_rl/workbench/environment.py)的`_state`/`_structured_context`、[卫星环境](../../../src/satellite_rl/envs/satellite.py)的`SGM_rate`。本轮科学源码参照为`ecb74e89e637dced320f2f8ea9892a55d28565d7`；未来实现须另行冻结真实新提交，不修改G09冻结源码。

## 4. 推荐的四组实验

以下S0–S3仅为提案内标签，还没有工作台任务ID。

| 组别 | 实际维数 | 在原204维上保留的字段 | 主要比较 |
| --- | ---: | --- | --- |
| S0 完整参照 | 207 | 平均需求＋处理进度＋剩余需求 | 同平台、同新实现的参照 |
| S1 去掉平均需求 | 206 | 处理进度＋剩余需求 | S1对S0：需求尺度信息的条件作用 |
| S2 去掉处理进度 | 206 | 平均需求＋剩余需求 | S2对S0：显式处理进度的条件作用 |
| S3 去掉剩余需求 | 206 | 平均需求＋处理进度 | S3对S0：后续总需求信息的条件作用 |

四组均为14个令牌：原13个加1个全局信息令牌。S0的全局投影接收3个真实数，S1–S3接收各自2个真实数；字段顺序在配置中显式冻结，不用第三个零占位。输入投影参数量随维数自然变化，隐藏宽度128及后续骨干不变。记录各网络参数量和初始化SHA；同种子不意味着不同形状网络的全部初始权重相同，不宣称等参数的纯信息因果实验。

统一训练种子51001，每组400000交互步，**四组共1600000步**；不增加训练种子，不从已训练N1热启动，固定40万步终点用于主比较。新S0需要重训，因为本次要与三个206维模型进行同平台、同实现的正式配对对照。

**可选第五组：204维原状态、13令牌。** 仅当本轮还要严格回答“三项全局信息整体相对原状态是否有益”时加入，同条件从头训练，总预算变成2000000步。四组主方案只回答单项条件作用；旧G09的204/207结果不能替代这个新整体对照。此组不默认包含在推荐预算中。

## 5. 共同条件与数据

- 环境：欧洲航空、100束、8组、每组100频率槽、25MHz/槽、3000W、原5–50W功率档、原联合掩码和最小资源预留规则。
- 学习：`legacy_repaired`旧奖励，dropout=0，`shuffle_each_cycle`；原Transformer隐藏宽128、8头、2层、前馈512；batch256、经验池20000、gamma0.99、tau0.005，Actor/Critic/温度学习率为1e-5/1e-4/1e-4。不同时改损失、温度、动作粒度或奖励。
- 训练仍使用2024-01-08/09的576个冻结场景；固定验证仍使用01-12的20个场景。保存逐回合场景SHA，核对四组场景顺序一致。业务需求仍为合成需求，不能把ADS-B轨迹称为真实通信流量。
- 最终考核在训练前预选、冻结一个尚未用于调方案的新日期及100个时刻，采用既有业务生成规则、seed51001和最大位置年龄60秒。候选可取2024-01-23，但本次尚未核验该日原包可用性，也未下载或导入。日期可用性与质量预检完成后锁定，不能看模型成绩再挑日期或场景。
- 01-19已用于G09分析和本次方案选择，后续只作开发参照；第一阶段用过的01-22也不作为全项目全新留出数据。单一新日期仍不足以证明全年或所有航区泛化。
- 主考核四模型各同100场景×3随机动作=1200次；固定/贪心各100次，只执行一次，合计1400次分配。先对同场景3次动作取均值，再按100场景配对。可选204加入时总数1700次。验证和内部开发评价单独计数，不算训练交互预算，不称新增训练种子。

本轮保持训练分布，是为了判断状态因素。等状态选择明确后，再单独比较多日期、低/高负载和第一阶段实际输出布局；不要本轮同时换训练数据而把收益都归给状态。

## 6. 开始前先做的诊断与工程检查

建议先利用G09已有场景、轨迹和日志做低成本诊断，无需重新训练：

1. 检查三字段在训练、验证、考核中的范围与相关性；按平均需求的低/中/高分层，阈值仅由训练集确定。
2. 按实际处理顺序分前20、中60、后20束，比较功率、频率槽和最终基本服务；核查服务不足是否集中在尾部、特定需求或高干扰波束，保留同束分配时与全场景结束后的差异。
3. 对照N0/N1的前、中、后训练窗口，检查剩余功率和后续需求的分配关系。已有记录不足的项目明确缺失，不拿补算估计冒充原始记录，也不自动增加长评价。

上述分析尚未执行，是实验前诊断，不是三项字段因果作用的证明。

当前自然状态配置只支持既定档位，不能直接选择这三个字段的任意子集。未来实施需同时接入：

- 前端可选的全局字段、实际维数/令牌/参数量预览，欧洲选项和旧奖励说明。
- 服务端合法组合校验，稳定的字段顺序；冻结任务、模型、完整断点与评价元数据记录相同字段集合。
- 策略、价值与目标网络真实输入/投影形状；禁止静默补0、忽略字段、错序加载和不匹配恢复。
- 新S0与旧207实现同权重、同场景、同动作的状态/奖励/前向等价检查；三206输入等于正确选取的真实两字段。检查删观测没有改环境的平均需求、奖励或资源账。
- 各组真实CUDA更新、保存/严格加载/完整断点恢复、旧模型兼容、实际页面提交配置与后端记录贯通；短检查与正式训练目录分开。

仅本次方案归档不新增页面操作，因此本次无需改前端；实施字段选择和验证节点时必须同步前端，不仅改后台切片。

## 7. 怎样判断曲线改善与模型有效

建议新增未训练的步0验证，并在2000、5000步及以后每10000步验证，后者含10000至400000，共43个节点。每节点同20场景×3动作，四组均使用同一协议。此调度当前尚未实现，必须在工作台配置、任务元数据和训练器同步接入；验证使用独立环境并保存/恢复全部训练RNG，避免验证次数改变学习轨迹。

每组至少展示：

| 图表/指标 | 固定口径与用途 |
| --- | --- |
| 训练原生累计回报 | 全部原始回合点＋向后100回合均值；每组独立面板，标明步数与窗口 |
| 固定验证原生回报 | 显示全部原始43节点，标清同场景随机动作口径；步0到末5点变化反映是否学到，不能与跨奖励数值混排 |
| 验证终态服务 | SI、SGM、基本服务束数与全100束达标率；后续干扰和未服务波束全部计入 |
| 学习诊断 | TD误差、双Critic损失、Q/目标尺度、温度α；低loss不等于业务效果好 |
| 独立考核 | 100个场景的配对差值分布，低/中/高需求分层，服务最差场景与波束分布；标清场景排序而非伪装成训练曲线 |
| 资源与约束 | 实际功率、频率槽、零槽、越界请求、裁剪、超预算、完整处理比例；请求与执行分别保留 |

分析规则在训练前锁定：统一报告相对步0的验证变化、1万–5万与36万–40万各5点均值、末10节点的范围/斜率。固定窗口，保留退步和离群点；平台但无增益只能称“表现趋稳”，回报与服务持续下降应记为退步，不能靠平滑变成成功。有限节点只能支持本次运行的平台特征，不能证明严格收敛或跨训练种子稳定。

选择时先检查无约束错误与基本服务，再联合看SI、SGM和资源：

- 删除字段后，固定验证持续退步、共同考核的SI或基本服务也下降，支持保留该字段。报告每场景升/平/降数量及差值，不只看总均值。
- 删除字段后，各服务指标没有明显损失并保持平台，可将206维列为简化候选；若只差很小，不凭一个种子宣称两者等效。数据中有服务/SGM/资源取舍时，应写明取舍，不强排唯一冠军。
- 三种删除都没有明显退步，也不能直接同时删掉三项；相关字段可能相互代偿。之后才考虑实际205维单字段方案，属于另一轮条件计划。
- 不强制功率用满，也不把功率变少直接算进步；必须同时检查全部波束的最终服务。不能把N1旧日期的91.56%直接当新日期的达标线。

定期使用独立环境评价并区分探索噪声，符合[Stable-Baselines3官方评估建议](https://stable-baselines3.readthedocs.io/en/master/guide/rl_tips.html)；少量运行下避免把单个点估计当稳定结论，可参照[Deep Reinforcement Learning at the Edge of the Statistical Precipice](https://arxiv.org/abs/2108.13264)。本方案沿用用户指定的单训练种子，文献不构成增加种子或更换算法的授权。

## 8. 后续优先级与执行边界

第一优先是本方案四组与基本服务诊断。若完整207仍最好，保留它作为后续主线；若206有一致优势，再做有针对性的精简。如果差异很小，就报告现预算下尚不能区分，不自动延长步数。

第二优先是根据诊断补最少、最有针对性的信息。例如确有末尾资源不足且现有状态未表达时，再单独研究每个剩余波束可用功率或基本服务概况；不能因为246维更全就再次全量加回。字段、预算与条件须另成方案。

之后才处理多日期/不同负载训练，以及第一阶段布局输出的衔接。在状态对照完成前，不同时换新奖励、固定温度、Huber损失、学习率或频率槽粒度；这些会引入另一组原因。历史新奖励的低功率失败仍须保留，不能因本轮平台改善而视为已解决。

未来正式任务统一经实验工作台提交，在指定4090D的DQN/CUDA环境由后台子agent协调持久进程执行；先核实际包路径、源码、CUDA及资源，按有效总吞吐决定四组并行程度。科学源码冻结，本地和远端Git及完整资产保留；不通过无意义计算填高GPU占用。不自动恢复已完成G09或其定时任务。
