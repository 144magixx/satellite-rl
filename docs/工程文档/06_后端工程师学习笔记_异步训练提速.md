# 后端工程师学习笔记：异步训练提速

日期：2026-09-29。**本文仅用于学习**，回顾已实施的工程优化，不提出新的训练任务或改动。读者只需熟悉后端请求、队列、缓存和持久化；SAC 的数学推导不是阅读前提。项目方案见[方案08](../第二阶段/方案/08_异步采集与训练吞吐优化设计.md)，实测方法与曲线见[验证报告05](../第二阶段/实验报告/05_异步采集与训练提速验证.md)。

## 先建立一个训练循环的心智模型

一个欧洲航空场景给出100个波束的位置和业务需求。模型依次选择波束的频率槽起点、连续槽数和功率，环境计算分配后的容量、干扰、需求满足率及奖励。一次动作及其前后状态进入**经验回放池**，SAC 从池中抽取样本更新策略网络和价值网络。这里的“步”是一次环境交互；“更新”是一次参数学习，两种计数应分开。G08每组预算40万交互步，回放预热后实际产生398001次更新。

训练循环可类比一个长期运行的服务：环境交互与参数更新是主业务；日志、指标和页面展示是观测；完整断点是恢复依据。类比有一个关键边界：训练后续的动作取决于当前模型、回放内容和随机状态，因此随意调整执行顺序，可能改变最后学到的策略。SAC 是使用经验回放的离策略算法；本项目还有离散、分解的频率槽和功率动作，具体实现以[本项目算法代码](../../src/satellite_rl/agents/workbench_algorithms.py)为准。[SAC 原论文](https://arxiv.org/abs/1801.01290)可帮助理解离策略与熵的背景，不能替代本项目的实现说明。

```mermaid
flowchart LR
    A[航空场景：位置与业务需求] --> B[策略选择频率槽与功率]
    B --> C[环境计算容量、干扰、奖励]
    C --> D[经验回放]
    D --> E[SAC参数更新]
    E --> B
    E -. 生成指标 .-> F[有界记录队列]
    F --> G[后台写日志与TensorBoard]
    G --> H[工作台读取和绘图]
```

| 后端概念 | 在这次训练中的对应物 | 不能照搬的地方 |
| --- | --- | --- |
| 请求主路径 | 选动作、环境交互、回放采样和参数更新 | 一次更新会改变之后的请求行为，顺序本身属于实验条件 |
| 消息队列 | 等待写入的日志、指标和状态 | 入队表示已接收，仍需刷新才能认为已落盘 |
| 周期快照 | 完整训练断点 | 单有模型权重不能从同一学习状态续训 |
| 配置版本 | 科学配置哈希和冻结源码 | 日志延迟属于操作配置，状态输入、奖励和场景顺序属于学习语义 |
| 读端缓存 | 监控页的增量指标与TensorBoard事件 | 页面展示点可能抽稀，原始文件才是核验依据 |

## 经验一：先找主路径上的等待，再决定异步化什么

原训练每次更新追加`updates.jsonl`，每50步记录指标和状态，也会做周期验证及保存。直觉上“文件写入慢”是合理怀疑，但逐段计时发现另一项更重：模型有很多参数和梯度张量，原代码反复让CPU等待GPU返回“这个张量有没有无穷大或NaN”。PyTorch的GPU操作通常先提交给设备执行；读取GPU标量到CPU，例如`.item()`，会形成等待点。[PyTorch CUDA语义说明](https://docs.pytorch.org/docs/stable/notes/cuda.html)解释了异步执行和正确计时所需的同步。

此次组合优化把适合的张量按设备和类型集中做有限值检查，再集中回传诊断标量。非空、连续、实数的CUDA浮点张量使用批量最大绝对值检查；空张量、复数、非连续张量、CPU张量及不支持该批量操作的情况退回逐元素检查。发现异常仍逐项定位。损失、梯度和参数仍检查，梯度裁剪阈值、优化器顺序和更新次数不变。代码入口：[有限值检查](../../src/satellite_rl/agents/workbench_algorithms.py)、[训练边界检查](../../src/satellite_rl/workbench/runner.py)。

这像数据库服务中的“逐行跨网络查询”改成“同条件批量查询”：收益来自减少许多次往返。**批量检查不等于取消安全检查**。如果为了速度删除NaN检查或减少更新次数，虽然计时会更好，实验已经换了问题。

计时也要符合设备的执行方式。只量“CPU把工作提交给GPU”可能提前结束，漏掉实际GPU计算；本次短测在计时边界等待CUDA完成，并计入异步队列关闭时的写出。逐函数计时可能相互包含，不应把所有分项秒数相加成总耗时。测速脚本和原始值在[基准测试目录](../../outputs/verification/async_telemetry_20260929/bench)。

## 经验二：有界队列解决主路径等待，背压解决失控增长

[AsyncTelemetrySink](../../src/satellite_rl/workbench/telemetry.py)先在训练线程捕获并序列化当时的记录，再交给单个后台写线程。单线程按入队顺序处理JSONL、TensorBoard和状态文件，避免后面的状态越过前面的指标。默认队列最多2048项，目标刷新间隔2秒。队列满时提交方等待，这是**背压**：它把慢磁盘的代价显式反馈到生产方，而不靠丢记录来掩盖问题。Python标准库的[有界`queue.Queue`](https://docs.python.org/3.11/library/queue.html)同样在容量用尽时阻塞生产方。

这里有三个不同的时间点：“记录的值已经固定”“记录已被队列接收”“记录已写入并刷新”。主线程必须在入队前固定数值，避免后台读到下一次更新之后的可变对象。状态发布前，写线程先刷新排在它前面的日志和TensorBoard，再原子替换`status.json`。验证、完整断点和结束前会等待写出屏障；后台写入错误返回给主线程。队列大小、阻塞时间、处理数量、最后刷新时间和错误在健康信息中可查。正常运行不抽样丢掉更新行；原生崩溃或断电仍可能损失未落盘尾部。

PyTorch的`SummaryWriter`本身支持[异步写事件](https://docs.pytorch.org/docs/stable/tensorboard.html)，但旧训练路径每次记录后显式`flush()`。这提醒后端工程师：**某个组件支持异步，不代表调用链就是异步**。本轮把TensorBoard的加入标量、刷新及关闭统一交给后台写线程；JSONL仍由本项目的队列管理。

## 经验三：断点是事务边界，日志要跟断点对齐

完整断点保存网络参数、优化器、经验回放、随机状态和进度。只存策略权重适合推理，不能保证续训后的抽样、梯度和场景顺序接得上。G08还把训练种子、实际场景、冻结源码与配置哈希绑定。日志方式`telemetry`保留在完整任务配置中，但不参与[学习语义哈希](../../src/satellite_rl/workbench/checkpoints.py)；改变显示延迟不会冒充改变奖励或状态空间。

假设断点在第10000步，进程后来写出了10100步的日志，但还没存下新的完整断点便退出。恢复时只能从10000步的模型、优化器、回放和随机状态重算；若保留10100步旧日志，新计算会产生重复记录。[恢复代码](../../src/satellite_rl/workbench/runner.py)会按断点步数裁剪其后的JSONL行，**包括完整写出的行**，并让TensorBoard隐藏回滚之后的旧事件。未写完整的最后一行可以丢弃，中间损坏不能静默跳过。

这与数据库事务快照相似，但不能把训练日志叫作“每步已提交的事务”。本项目在完整回合边界保存断点；两个断点之间如果进程突然退出，可能需要重算这段训练。实际曾有任务在0步遭遇原生CUDA模块退出：工作台保留故障和Windows事件记录，检查完整初始断点后用同一任务ID排队恢复；仅凭退出码不能断定根因。[现场记录](../../outputs/experiments/europe_ablation_20260929/recovery_20260929_1350/recovery_summary.json)展示了服务进程、worker和外部驱动故障的边界。

验证和完整保存目前仍同步。把`save_checkpoint()`直接扔给线程，线程可能在优化器继续修改参数时读到不同时刻的模型、回放和随机状态。若将来要并行保存，应先制作不可变、同一版本的快照，再证明恢复结果一致；还要计算复制内存和GPU争用成本。

## 经验四：页面读端提速是另一条链路

页面过去多次全量解析指标文件。[MetricsReader](../../src/satellite_rl/workbench/monitoring.py)对主指标`metrics.jsonl`记住文件身份和读取偏移，只读取追加的完整行；截断或原子替换后重建缓存。TensorBoard事件读取器复用并在文件变化时加载。缓存最多保留4个运行、合计约100万点；TensorBoard每标签有事件上限，长曲线在页面还会减少显示点数并保留分段极值。事件日志、worker输出和历史CSV没有全部改成增量读取。原始数据继续保存在文件中。

复制正式日志做的读端检查中，旧全量读取约1.5–1.7秒，新版首次约1.56秒，缓存命中或小量追加约0.05–0.07秒。[读端原始计时](../../outputs/verification/async_telemetry_20260929/monitoring_profile.json)。这是用户打开监控页时的收益，**不能加进训练更新的提速倍数**。前端还增加同步/异步选项、2秒目标刷新间隔和缓冲容量，服务端校验后写入任务与模型元数据；实际展示延迟还取决于每50步采样和页面轮询。[前端实现](../../src/satellite_rl/workbench/static/app.js)、[方案与页面核验](../第二阶段/方案/08_异步采集与训练吞吐优化设计.md)。

## 经验五：性能数字、数值正确和模型效果分开验收

同一初始状态、种子及欧洲实际场景下，两类网络各做3轮A/B/B/A交替短测，合计24次、12个配对；每次含500次真实环境交互和500次SAC参数更新。短循环还记录同频率的日志和场景，结束时等待队列写完。原版本与组合优化的中位耗时如下，GPU上同时有三项正式训练在竞争资源。

| 状态布局 | 原版500次更新 | 优化版500次更新 | 同工作量吞吐倍数 |
| --- | ---: | ---: | ---: |
| 13令牌 | 94.56秒 | 35.53秒 | 2.66倍 |
| 32令牌 | 113.67秒 | 46.29秒 | 2.46倍 |

单独改异步记录的首对速度变化不稳定；组合优化的主要收益来自减少GPU等待。相邻短窗口里，保留记录相比关闭观测I/O的“纯算法参考”，仅多耗时约0.7%/2.1%；每种布局这里只有一对，且参考关掉了正式任务需要的观测。正式三任务在另一组约120秒训练窗口的总更新吞吐由19.75升至37.83次/秒，约1.92倍；两个窗口训练位置不同。周期验证和完整断点仍占用时间。**这些数字分别回答不同问题，不能推成“40万步训练一定快2.66倍”。** 全部原始计时和限制见[验证报告05](../第二阶段/实验报告/05_异步采集与训练提速验证.md)。

数值正确也单独检查：同一场景中的动作、奖励、网络、优化器、回放池、随机状态和指标在短试验中一致；两类网络还验证了从完整短断点继续更新、验证和保存。351项CPU回归中1项跳过，其余通过，另有真实CUDA更新检查。迁移时工作台逐文件核对“原冻结版→实测worker版→正式接续版”的源码和证据，按**同一任务ID**保留断点、场景、种子和40万步预算；完整历史在[接续证据](../../outputs/verification/async_telemetry_20260929/migration/final_handoff.json)。这些工程检查不能证明新的状态空间或dropout设定会提高最终需求满足率。那要等六组固定预算结束，在共同的独立考核场景比较SI、SGM、基本服务束数和资源约束。训练loss变化也不能单独证明模型已收敛。

## 留给后端工程师的三个自测题

1. **队列已接收第10001步日志，磁盘还没刷新；此时进程直接退出，能否承诺这行存在？**不能。判断恢复范围要看最后完整断点与磁盘上的有效记录。
2. **监控页只显示少量点，能否说原始日志被抽样丢弃？**不能。页面显示会减少点数；项目的正常异步写入路径不靠丢原始更新行提速。
3. **两个实现的参数更新一样快，能否直接说其中一个算法效果更好？**不能。速度比较检查同工作量；学习效果要在同场景按全部波束终态指标和约束单独比较。
