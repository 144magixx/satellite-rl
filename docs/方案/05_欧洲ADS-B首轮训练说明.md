# 欧洲ADS-B首轮训练说明

日期：2026-09-28。实验编号：G07，目录`europe_adsb_20260928`。

**这轮要做的事：让模型在不同欧洲航空器分布和业务需求下，练习怎样分配频率槽与功率。** 用户已要求导入ADS-B场景并开始训练。本说明在训练提交前编写；当前正在下载、清洗和核验数据，训练尚未提交。实际场景数量、三个场景集编号及最终配置在正式提交前补齐；任务编号及确认冻结的提交号在创建任务后补记，不以计划数冒充完成数。

## 1. 哪些是真的，哪些是假设

| 内容 | 本轮采用什么 | 怎样理解 |
| --- | --- | --- |
| 航空器位置和时间 | ADSB.lol公开历史记录 | 是接收网络观测到的位置；覆盖不到或缺报的飞机可能未记录 |
| 每架飞机的通信需求 | 人数、接入比例、活跃比例和速率模型 | 属于明确的合成业务假设，不是机上互联网实测流量 |
| 波束中心 | 本轮用规则方法生成100个中心 | 覆盖策略不属于本轮训练，尚未接入开题报告第一部分的覆盖算法 |
| 频率槽与功率 | 由T-SAC模型逐束选择 | 这是本轮真正要训练的部分 |

因此，这轮的数据应称为**“公开航空位置驱动的合成通信业务场景”**。得到的模型先说明它在这批数据和业务假设下的分配能力，不能直接代表全部欧洲航线、所有季节或真实运营商业务。

## 2. 数据从哪里来，怎样分开使用

选取[ADSB.lol官方历史归档](https://www.adsb.lol/docs/open-data/historical/)中的[2024年归档](https://github.com/adsblol/globe_history_2024)，使用官方推荐的同一个`planes-readsb-prod-0`实例，避免把多个接收实例重复叠加。数据页标注ODbL 1.0。四个原始日包的发布大小合计6,184,642,560字节（约6.185 GB），低于8 GB下载预算；实际下载完整性及SHA-256记录在实验目录。

| 数据用途 | UTC日期 | 预先确定的取样方式 | 用来做什么 |
| --- | --- | --- | --- |
| 训练 | 2024-01-08、01-09 | 每天00:02起每5分钟取一次，至23:57，每天288个、两天合计576个候选时刻 | 模型反复练习，可用于参数更新 |
| 验证 | 2024-01-12 | 从当天相同时间网格均匀预选20个时刻 | 训练过程中检查进展、保存验证最好权重 |
| 最终考核 | 2024-01-15 | 从当天相同时间网格均匀预选100个时刻 | 训练结束后评价固定40万步的最终权重 |

日期、取样网格和用途先确定，再处理数据。不能因为某个场景分数低就删掉，也不把同一天的相邻快照随机拆到训练和考核两边。训练与验证、验证与考核之间各留出两天间隔，减少同一段跨夜航迹造成的时间泄漏；航空器身份本身可能在不同日期重复，不能声称是全新机队。当前只选冬季四个工作日，首轮不据此声称已验证周末、节假日或跨季节泛化。

候选时刻若因有效飞机不足、没有100个不同正需求位置等原因被拒绝，会保留时刻和原因。训练实际采用通过数据质量检查的场景；验证和最终考核数量必须在提交前明确，不能静默补造飞机或需求。逐帧处理可避开单次大文件内存限制，不改变取样网格。

## 3. 怎样从航迹变成波束需求

```mermaid
flowchart LR
    A[历史航空位置] --> B[同一时刻的有效飞机]
    B --> C[每架飞机的合成需求]
    C --> D[100束覆盖与唯一归属]
    D --> E[每束中心和总需求]
    E --> F[模型分配频率槽与功率]
```

**第一步，取一个时刻的飞机分布。** 每架飞机只用指定时刻之前最近的观测，最大允许记录年龄为60秒；不用未来位置。统一UTC、经纬度和高度单位，去重并记录非法、地面、陈旧、过期及不可服务的记录。晚出现的无效位置不会用旧有效位置顶替。采样是静态近似，不插值，也不自动预测未来位置。

**第二步，给每架飞机估算需求。** 本轮统一使用下列参考值，均为工程假设：

| 参数 | 数值 |
| --- | ---: |
| 每架航空器参考人数 | 180人 |
| 卫星业务接入比例 | 20% |
| 接入用户中的活跃比例 | 30% |
| 每活跃用户平均需求 | 2 Mbit/s |
| 额外机载基础业务 | 0 Mbit/s |
| 人数抽样 | 按人数和比例随机抽取活跃人数 |
| 额外需求波动 | 对数正态乘性扰动，标准差参数0.35，保持期望倍率为1 |

期望需求的直观算例是`180×20%×30%×2=21.6 Mbit/s/架`。实际每架飞机还受人数抽样和额外波动影响，不是都固定为21.6。没有把机型或实际载客率当作已知信息；原始数据如有机型仅保留统计，本轮统一参考人数不能解释为实际乘客数。

需求随机种子固定为51001，并由每个UTC时刻派生随机流，处理顺序改变不会随意更换这一时刻的需求。每份实际数组会保存，因此以后可以精确复现。需求按60秒窗口的平均请求速率理解；本轮不模拟数据包队列或连续会话。

**第三步，生成100个波束中心。** 先从需求较大的位置开始，再兼顾离已有中心较远、需求较高的地方，选100个代表位置。中心来自现有飞机的地表投影；这是一套过渡规则，不保证覆盖最优，也不是第一部分DRL算法的成绩。

**第四步，确定覆盖和汇总需求。** 每架飞机分给卫星视角最近的波束；离轴角不超过0.25°才算覆盖，每架飞机只计入一束。把同一束内各架飞机的需求相加，得到该束需求。覆盖不到的飞机及其需求单独保留，并核对：

`全部有效飞机需求 = 各波束需求之和 + 未覆盖需求`。

最终把100束按需求从大到小排列，同步位置、距离及身份；资源组沿用处理序号对8取余的规则。模型输入中的“需求”是目标值，实际能提供的容量由分配结果和干扰计算决定。

## 4. 欧洲环境是什么样的

欧洲版使用独立的`europe_v1`环境：GEO经度13°E，外包范围25–80°N、40°W–50°E，并要求至少10°仰角。范围及仰角条件都要满足。卫星位置、星地距离、干扰方向和位置归一化对应欧洲版本。

仍保持100束、8组频率资源、每组100槽、总功率3000 W、每束0.5°全宽。每次动作选择频率槽起点、连续槽数和一个功率档位。模型使用原204维输入：当前束位置/需求、剩余功率、当前组的逐槽干扰和占用；尚未增加完整的未来波束位置/需求。

当前链路仍把每束中心当作代表用户，航空器高度只作筛选和记录，几何采用地表投影。结果是波束层面的资源分配近似，不能直接称为每架飞机实测速率。

## 5. 模型怎样训练

模型采用已验证的原T-SAC结构：13个输入令牌的Transformer、旧奖励`legacy_repaired`、联合动作掩码及最低资源预留。掩码会排除占用冲突、越界和超过预算的选择，并为后续波束留最低资源。

| 设置 | 本轮安排 |
| --- | --- |
| 训练数量 | 只训练1个欧洲模型，从头初始化 |
| 训练种子 | 51001，不增加其他训练种子 |
| 训练预算 | 400000次环境交互，约4000次完整100束分配 |
| 前期探索 | 前2000步积累经验，之后按配置持续更新网络 |
| 学习批次 | 每次从经验池抽256条记录学习 |
| 保存与验证 | 每10000步保存断点，并检查20个验证场景 |
| 主要模型 | 固定40万步的最终权重；验证最好权重另存，不拿考核集挑模型 |
| 设备 | 用户指定的DQN环境与RTX4070SUPER CUDA |
| 执行方式 | 工作台/API正式任务、冻结源码、后台子agent负责启动与核验 |

一回合先固定一份位置和需求，模型依次给100束分配资源，再得到这一轮服务和资源结果。下一回合切换到下一份保存的场景。用完训练场景集后循环使用；**40万步不代表40万份独立场景，也不代表4000个不同业务时刻。** 实际循环次数以保留场景数计算。

训练期间的验证不更新模型参数；每个验证场景做3次随机动作采样，用来观察同一场景下策略的表现。正式训练由持久后台进程执行，浏览器关闭不会中断；电脑关机或睡眠仍会中断计算。本轮不会安排关机。

## 6. 最后怎样判断表现

训练结束后，固定终点权重在100个考核场景上各运行3次随机动作，保存逐束数据。主要观察：

- 全部100个目标波束最终的需求满足率，包含后来产生的干扰。
- 供需匹配程度，单独报告，不与需求满足率混为同一指标。
- 达到本束需求10%的波束数，以及是否所有100束都达标。
- 零容量束、实际功率、频率槽消耗、冲突/越界和完整分配情况。
- 覆盖阶段的未覆盖飞机及需求，单列说明，避免只看已覆盖波束的好成绩。

这一轮首先建立欧洲航空条件下的训练结果。只有一个训练种子，不能宣称重训稳定性；也不能把新欧洲分数直接与旧中国场景的75.55%比较，进而认定算法变好或变差。后续如要证明数据方案改善泛化，须另做同一欧洲考核集上的受控对照。
