# 训练场景泛化与第一阶段衔接方案

日期：2026-09-28。状态：**方案建议，未实施、未启动新训练，效果待验证。** 本次按 `satellite-rl-change-eval` 的方案审查与纯文档分支核查；不改变G01–G06结果，也不批准P01奖励实验。

## 1. 建议与当前证据

建议把训练数据从“固定100城市＋独立抽取每束需求”改为“服务区域的业务分布＋有约束的波束覆盖方案＋按覆盖归属汇总需求”。先保持100束、固定波束宽度和现行资源预算，训练跨布局、跨需求分布的资源分配能力；再接入第一阶段实际输出的波束指向和宽度；最后扩展连续时间调度。

目前不能直接断言模型在新地理下表现很差：现有正式考核尚未覆盖该情况。能确认的是，训练与考核的地理范围有限，尚无任意新地理、航空业务或连续流量的泛化证据。

| 已核对事实 | 对方案的影响 |
| --- | --- |
| G01固定100城市集合；每回合独立抽100–1000 Mbit/s档位并加标准差20 Mbit/s扰动 | 固定的是生成分布；加大噪声不能代替改变热点、空间相关性与业务总量 |
| 需求降序后按处理序号%8分组 | 城市组别会随需求变化；必须分别保存身份、顺序和组别，不能把排名当作稳定身份 |
| 204维包含本束位置/需求、剩余功率、当前100槽干扰与占用 | 不是完全没有地理信息，但缺少未来波束位置/需求及完整干扰关系 |
| 已能导入100束CSV/NPZ；训练依次循环场景文件，当前导入上限1000份 | 导入小文件集不会自动产生4000份不同需求；需要版本化场景生成与调度配置 |
| 训练内置验证与终点评价仍由默认城市生成 | 必须补齐新验证/考核场景选择，或使用工作台独立评价任务显式指定共同场景 |
| 当前固定0.5°波束宽度，直接链路以波束中心代表用户且对准 | 可变坐标可先验证；可变宽度及真实用户偏离中心还需相应物理参数和校验 |

上述生成、环境、场景导入和训练入口与G01有效冻结提交 `5da891fdbcf5fa0255d912677840620d977367c9` 的对应文件校验一致。日常工作区另有文档归档等未提交内容，本方案不接管这些改动。

## 2. 与开题报告第一部分怎样衔接

[开题报告](../资料/01_开题报告_导出1212最终版.docx)第2节“研究内容”第一部分优化波束指向和宽度，第二部分基于覆盖方案，把覆盖小区用波束中心处的“超级用户”表示，输入汇总需求并分配频率与功率。报告明确提及不同时刻的业务数据及ADS-B航空数据；未找到可复现的航班到Mbit/s换算规则。本仓库 `data/` 目前仅见城市表，未见航空数据文件；报告称“现有”不等于仓库已接入。

```mermaid
flowchart LR
    A[用户或航空器的位置与业务需求] --> B[某一时刻的业务分布]
    B --> C[第一阶段覆盖规划]
    C --> D[波束中心与宽度 用户归属 每束汇总需求]
    D --> E[第二阶段频率槽与功率分配]
```

第一阶段尚未接入时，可用满足服务区域、可选波位、覆盖和波束间距约束的需求加权聚类/启发式覆盖器产生过渡数据。记录覆盖器版本、参数与失败场景，不能称为第一阶段DRL结果。仅围绕原100城市抖动用于局部稳健性检查，不作为主要地理泛化数据。

每个场景保存两层数据：底层用户/栅格的位置和需求；上层覆盖方案、稳定波束ID、用户归属、每束需求、资源组/极化及处理顺序。第二阶段仍可使用中心代表用户的近似，但应明确它不等同于真实束内所有用户的通信性能。

## 3. 业务需求怎样生成

### 3.1 分开控制总量与空间分布

先确定场景总需求，再决定需求集中在哪些区域，最后加入局部波动。一个可复现的候选表达为：

\[
q_g(t)=L_t\,\frac{w_g(t)}{\sum_h w_h(t)},\qquad
w_g(t)=\left[b_g f_g(t)+\sum_k A_k(t)K_k(g,t)\right]\exp(\epsilon_g(t)).
\]

其中，`g`表示地面栅格或服务单元；`L_t`是总业务需求；`b_g`是基础业务权重；`f_g(t)`表示时段变化；热点核`K_k`控制热点位置与范围；`A_k`控制强度。只在有业务的区域归一化，无业务场景另行处理。正值波动可采用对数正态或Gamma分布；相邻区域共享一部分波动，使附近需求一起涨落。公式是建议的合成模型，参数尚未从真实数据标定。

需要覆盖以下业务类型，避免只换成另一种固定分布：

| 场景类型 | 要变化的因素 | 对资源分配的考验 |
| --- | --- | --- |
| 较均匀、分散 | 总需求、局部起伏 | 常规公平分配 |
| 单热点/多热点 | 热点位置、个数、半径、强度与距离 | 邻近高需求束同时竞争资源 |
| 航路与枢纽 | 航路方向、航空器密度、枢纽聚集、时刻 | 沿狭长区域集中且随时间迁移的需求 |
| 稀疏与突发 | 活跃区域比例、局部事件位置与持续时间 | 低负载、极不均衡及局部资源不足 |

每回合抽取场景类型及其参数；相同类型中仍要改变参数。初期按类型分层采样，待获得目标业务统计后再调整出现频率。训练分布始终是有限范围，目标是覆盖部署中合理的变化，而非承诺任意分布都能适应。

当前100束期望总需求约55 Gbit/s，可暂用0.5、0.75、1、1.25、1.5倍作为低至高需求候选档位；这些只是实验设计数值，不代表真实卫星负载或可行容量。先用规则基线和资源分析检查难度，分别保留常规场景及供给不足压力场景。控制总量后比较空间集中程度；比较总量影响时尽量保持空间形状，避免难度变化混在一起。不能将所有地图重新缩放为同一总量后又声称验证了负载泛化。

### 3.2 优先衔接航空业务数据

优先核对开题报告所指的ADS-B原始资产。若暂不可用，可选择有访问条件说明的公开轨迹数据，先核对目标空域和日期覆盖，再确定数据范围。OpenSky提供航空器位置数据及科研数据入口，但完整历史数据访问有条件，缺测不能直接当作该区域无飞机。[数据入口](https://opensky-network.org/data)、[访问及覆盖说明](https://opensky-network.org/about/faq)。

ADS-B提供位置与轨迹，不等于卫星通信需求。建议显式建模每架航空器需求，例如“预计使用业务人数×活跃比例×每活跃用户平均速率＋机载业务需求”，参数由已有业务依据标定，暂缺依据时保留低/中/高三档假设并做敏感性评价；不得把ADS-B报文数量直接当作Mbit/s。

若以后扩展地面业务，可用[WorldPop人口栅格](https://www.worldpop.org/choosing-the-right-worldpop-population-data-for-you/)作为空间权重之一，再叠加卫星接入比例和单用户需求。人口数据本身不是卫星用户数据。真实位置＋假设需求应标为“真实位置驱动的合成业务场景”，只有确有通信流量测量才能称实测业务流量。

### 3.3 按覆盖归属汇总，保持业务总量

\[
D_i(t)=\sum_u a_{ui}(t)d_u(t),\qquad 0\le a_{ui}(t)\le1,\quad \sum_i a_{ui}(t)\le1.
\]

`a_ui`表示用户业务由波束i承担的比例；单波束关联时取0或1。重叠覆盖时不能把同一个用户的整份需求重复计入多个波束。覆盖不足部分单独记录。改变波束中心/宽度以后重新建立归属并聚合需求，不能把旧需求随意贴到新位置。即使底层热点明显，覆盖规划若主动均衡负载，上层每束需求也可能趋于接近；两层统计都要保留。

当前接口要求100束正需求。第一版可以明确限定为100束均有正需求的子场景；这只是过渡范围，须记录覆盖器筛除及空束情况，不能代表稀疏全场景。完整稀疏场景需要支持非活跃束和需求为零的统计规则，不能给空束人为填入100 Mbit/s。波束数变化及零需求处理另立版本。

## 4. 地理、信道与时间的边界

第一版在卫星实际可服务区域内改变波束中心、布局疏密和热点相对位置，仍固定100束、0.5°宽度、8组资源、每组100槽和3000 W。采用物理距离/角度约束，不在经纬度矩形内无限制独立抽点。相同布局更换需求、相同业务图采用不同合法覆盖方案，分别形成可解释对照。

目前位置改变会影响星地距离、天线方向角和干扰，重置会清空几何缓存；不存在一张需要沿用的固定城市信道表。导入新场景仍要核对坐标与距离一致、卫星可见性/仰角、波束指向和干扰计算。现有经纬度范围校验不等同于服务区域或可见性校验。

第二步接入可变宽度时，宽度、增益/方向图、覆盖关系必须一致。当前NPZ没有逐束宽度和用户归属字段，CSV默认增益50/40，不能仅改变覆盖圆或坐标就声称接入完成。中心代表用户仍是近似；有必要时再加入束内代表点或逐用户评价，航空器高度的处理也须明确。不要同时无依据地随机所有信道参数。

初期“一回合”仍表示某个业务时刻的一次完整分配：位置、需求、覆盖方案在100次分配中保持不变，下回合换场景。模型训练时打乱不同日期/时刻的快照可以提高覆盖范围，但不能据此声称学到了时间连续策略。

后续真正研究动态调度时，另行定义业务刷新时间间隔、覆盖与资源重配置周期，保留相邻时刻的轨迹/需求相关性、上一时刻资源及切换代价，并评估配置抖动、业务连续性和计算延迟。当前100个动作是分配给100束的步骤，不是100个真实时间点；不应每分完一束就让全场用户移动一次。

## 5. 与数据配套的状态输入

先检查旧204维在新布局中的适应性，不预先把所有失败归因于网络。跨布局分配需要知道当前动作对其他波束的影响；仅增加场景数量不能补齐未观测信息。

短期可利用工作台已有附加特征加入分配进度、剩余束数、剩余需求、资源组、其他组占用与已服务束缺口，作为低成本过渡。但这些汇总仍不能完整表达相邻波束的需求和相互干扰。

面向第一阶段接口，优先设计按波束组织的输入：每束位置/相对方向、需求、宽度或相关信道特征、组别、已分配状态、频率/功率及当前已服务波束的需求满足缺口；未分配波束提供需求与未分配标记，另提供全局预算和两束间可计算的干扰关系。干扰关系不一定要全部直接展开为固定长向量，可由波束特征及注意力/邻接信息组织。只有依据当前已知场景及历史动作计算的量可输入，不能泄漏未来未执行动作产生的结果。

G01原13令牌布局被配置校验限定为204维；追加信息涉及输入/网络版本和重新训练，不能宣称直接兼容原权重。数据对照的两组必须使用相同状态、网络、奖励和掩码。若状态改变，旧数据对照也要在相同新输入下重训，G01旧权重仅作历史补充参照。

## 6. 怎样证明泛化改善

先划分底层日期、区域和轨迹/场景家族，再生成扰动和覆盖方案。相邻时刻、同一轨迹片段、同一业务图的多个覆盖方案应留在同一分区；空间区域留出时设置边界缓冲，避免近邻泄漏。数据标准化、分布参数、热点模板和覆盖器的拟合都只使用训练集。训练、可反复查看的验证集、封存考核集各自保存实际数组及SHA-256；换随机种子不能单独保证独立性。

| 考核组 | 变化范围 | 结论用途 |
| --- | --- | --- |
| 原范围 | 原城市库的新需求组合 | 检查原任务能力是否明显退化 |
| 同类型新样本 | 训练允许的布局和需求类型、未见实例 | 检查正常泛化 |
| 新地理布局 | 留出区域/布局家族，控制总量和需求形状 | 检查位置变化 |
| 新业务分布 | 控制布局，留出热点或需求集中模式/参数范围 | 检查需求变化 |
| 联合变化 | 留出的区域、日期与业务分布共同变化 | 检查面向部署的困难场景 |

独立报告航空轨迹驱动考核、合成常规场景和压力场景；不能平均成一个分数掩盖某类失败。第一版可候选每类20个独立场景，共100个，每模型每场景3次动作采样；不足以代表全部真实空域，数量可在正式方案中固定，不能根据考核成绩临时挑选。重复动作不是独立场景，单训练种子也不能支持跨训练种子的稳定性结论。

所有方法使用同一批最终考核场景，包含旧模型（输入兼容时）、新模型、原规则基线和必要的需求感知基线。报告全部目标束的终态平均需求满足率、SGM、达到10%基本服务的束数及全体达标比例、最低/低分位服务、零容量束、吞吐与有效吞吐、总功率、冲突/越界/完整分配率及推理时间。存在零需求时先固定统计分母与非活跃束规则；束数变化时分别列束数及均值。

第一/二阶段联合评价还须把未覆盖用户需求记入端到端服务指标，避免第一阶段丢弃难服务用户后第二阶段分数虚高。资源不足压力场景单列，低服务率不自动等于策略失败。

## 7. 建议的最小实施顺序与预算

1. **先做场景模块与核验。** 保留G01源码、配置和权重，建立有版本的生成器/覆盖转换器、来源与划分清单。补齐训练/验证/考核的场景接口、工作台配置和服务端校验、冻结配置、断点/模型元数据。字段包含数据版本、总量分布、热点/航路参数、覆盖器、时间间隔、排序/组别规则及随机源；实际场景保存到任务目录。核对场景循环与恢复，不能仅记录种子。
2. **冻结第一版范围。** 100束、固定宽度与预算；一回合一个静态业务快照。保留旧奖励＋联合掩码，不与P01奖励变化混在一起。身份、排序、组别/极化分离；第一版沿用需求降序与序号%8规则并如实标为现有工程约定，后续再单独研究地理相关分组。
3. **先做两组同预算比较。** A使用原数据，B使用多布局＋多需求分布；两组共用选定的输入/网络、学习与物理口径。候选各seed51001、40万步，共80万步，固定预算终点为主结果，不自动增加训练种子。若原实现/输入/预算完全一致并验证可比，可复用G01作受限参照；否则两组均从头训练。相同评价场景上比较，不直接引用G01历史75.55%与新场景分数排名。
4. **有改善后再拆因素。** 需要区分地理和需求各自贡献时，再补“固定地理＋新需求”与“新地理＋旧需求规则”两组，形成2×2对照；后两组尚未授权。仅两组时结论属于数据整体方案，不能归因单个变化。
5. **接第一阶段实际输出。** 先把真实覆盖策略生成的快照纳入训练/留出考核，再扩展宽度、非活跃束及必要的可变束数；最后研究连续重配置。合成覆盖器到第一阶段策略存在分布差异，必须用实际第一阶段输出再验证，不能只靠加噪保证迁移。

正式实施前须通过确定性检查：需求聚合守恒/重叠不重复计数；坐标、距离、角度与单位；新布局下干扰和终态重算；身份、排序、组别同步；零/高需求与资源不足；数据分区无近重复；断点恢复场景顺序；真实参数更新及新旧权重兼容边界。短检查只证明计算与接口正确。

正式训练和配套长评价继续由后台子agent经工作台/API运行，冻结源码并核对DQN/CUDA、导入路径及单GPU资源。验收优先约束合法和基本服务，在此基础上看各类场景SI/SGM与资源代价；事前确定可接受退化幅度，不能看完考核才改标准。以上预算及后续实现均为候选，**本次用户只请求方案，未启动任何任务。**
