## 2. 链路模型v2（`shared_interface/`）

在`spherical_gaussian.py`新增`PHYSICS_V2`（另一个版本号与内容摘要，不改原`PHYSICS`）：噪声温度631 K，新增频谱效率上限4.5、实现损耗1 dB、接收端说明"成员平均离轴增益"。所有校验处按版本识别v1或v2，v1路径一律不变。

**两处物理变化：**

1. **接收端从"波束中心"改为"成员平均"。** 设波束b的成员飞机为A_b，θ(a, j)为飞机a相对波束j指向的离轴角。v1里，b的信号系数用b在θ=0处的峰值增益，b受j干扰的系数用j在"b中心方向"的增益。v2改为对成员取线性平均：
   - 信号：mean_{a∈A_b} G_b(θ(a,b))
   - 干扰（接收b、发射j）：mean_{a∈A_b} G_j(θ(a,j))
   - 路径损耗、频率、槽重叠、同极化异组才干扰等规则与v1完全相同。
   - 这需要飞机位置和归属：从`case`的`lat_lon_deg`和`layout`的`owner_aircraft_to_beam_id`取。把这部分并入`prepare_slot_kernel`的预计算（与分配无关，每景只算一次），`raw_slot_coupling`与`build_link_coefficients`照用kernel即可。
2. **容量**：每个占用槽 C＝B×min(log2(1＋SINR×10^(−0.1)), 4.5)。`capacity_bps`与`power_refinement/physics.py`的`FixedAllocationPhysics.evaluate`都要支持（后者在构造时传入频谱效率上限和损耗；Jacobian在封顶的槽上为0）。

**服务口径**：束内各飞机请求相同，按"等吞吐分时"服务，每架飞机的满足率等于所在波束的min(C/D, 1)。逐飞机指标由逐束结果按成员数展开。

**测试**：小场景上随机功率，`capacity_bps`（v2）与`FixedAllocationPhysics.evaluate`（v2）结果一致；v1结果与改动前逐位相同。

## 3. 第一阶段FLOW-AO v2（`coverage/s1fix/skeleton.py`）

在现有`solve`上加三个选项，默认关闭以保持旧行为：

1. **`per_beam_cap=K`**：网络流里每个波束到汇的容量改为min(T, K)；`assign`、`_at_peak`、增束、删束都用它。
2. **`objective="narrow"`**：交替优化里把"负载平方和最小"一步换成"在每束负载≤min(当前峰值, K)的前提下，总夹角Σθ(a, c(a))最小"（同一个LP，去掉单位弧的递增费用，距离项权重改为1），再重定中心。目的是波束尽量窄。
3. **`stacking=True`**：先以预算N−S求解（间隔规则照常）；对负载>K的波束b，在b的中心原位加ceil(load_b/K)−1个副本，副本与b覆盖半径相同、合格飞机集合相同，b与副本之间用网络流（容量K）分配原b的成员；b与它的副本记同一个`stack_id`。半径上限按"不同站点"计算：同一叠放簇的波束算一个站点，彼此距离不参与`coverage_radii`，簇内不检查间隔规则。保留量S依次试0、5、10、…、50，取使全部波束负载≤K的最小S；50仍有超限就用S＝50并在输出中记录超限波束数，不报错。

输出布局增加`stack_id`（不在簇内为−1）。`validate_layout`加`per_beam_cap`和`stack_id`参数：簇内豁免间隔检查，其余照旧。

**测试**：密集小例（一个点附近30架飞机、K＝8、预算10）应产生叠放簇且全部负载≤8；关闭三个选项时与改动前逐位相同。

## 5. 容量感知贪心G1（`s2fix/greedy.py`）

从S1-FIX分支`s1fix`的`coverage/s1fix/downstream.py:greedy_allocation`移植并修改：

1. **分组**：按需求从大到小，逐束在8组中选代价最小者。代价＝该束与已分配"同极化、不同组"波束之间的耦合增益之和（两向增益取大）＋该组已请求槽数超过100的部分×大惩罚。叠放簇内两束耦合增益就是峰值，所以自然会被分到不同极化或同一组。
2. **槽数**：估计该束按需求比例分到的功率P_b（3000 W按需求比例，封顶50 W），从k＝1起逐个试：k个槽在噪声受限下的容量k×B×min(log2(1＋SNR_k×10^(−0.1)), 4.5)（SNR_k用v2信号系数、P_b/k每槽功率），取刚好≥需求的最小k，到10封顶。某组请求超过100槽时按需求比例缩减，每束至少1槽。
3. **起点**：组内按需求顺序连续放置，起点取与"同极化其他组已占槽"加权重叠最小处（权重为耦合增益），沿用原实现。
4. **功率**：按需求比例分3000 W，每束封顶50 W，超出部分按比例分给未封顶的束，迭代到收敛。

输出：groups、starts、counts、powers（逐束数组，顺序与layout的beam_ids一致）。

## 6. 公共评价与第三阶段（`s2fix/evaluate.py`）

- `metrics(stage_input, groups, starts, counts, powers)`：用链路v2算逐束容量C，返回：**业务量加权满足率W＝Σmin(C,D)÷ΣD**（主指标）、波束平均SI、SGM（原定义）、最差10%飞机平均满足率（逐飞机满足率＝所在束min(C/D,1)，取最低的10%飞机）、满足率≥0.9的飞机比例、总功率、总槽数、同极化异组重叠槽数。
- `run_sca(...)`：用v2系数构造`FixedAllocationPhysics`，调`optimize_power(problem, p0, "sca", options)`，options含`maxiter=200`、`time_limit_seconds=30`，以及新增的**`beam_power_cap_w=50`**：在`power_refinement/model_based.py`的`_sca_proposal`里把每束功率变量上界设为50 W（缩放后为50/scale），接受新功率前检查每束≤50 W。不传该选项时行为不变。
- 每次评价记录分段耗时：初解、搜索或推理、SCA、总计。

## 12. 修订一：叠放算法改为"按需加副本"（2026-10-18 03:20）

**白天实测问题**：开发集最大场景（1815架，86.4 Mbps，K＝13，预算150）只生成了100束、最大束26架、72束超K、叠放簇0个。原因：(1) 单景时间上限被均分给11档保留量，每档约11秒，不够把束加到150；(2) 叠放把整个超限束原样复制，负载14架的束也要整束复制，副本总数轻易超预算，结果一个都没叠。

**新做法（替换`_solve_v2`里的保留量循环与`_stack_layout`）：**

1. **估计保留量。** 先以预算N、间隔规则、原峰值目标（不加K）跑一次FLOW-AO得到布局A；以A的中心与半径上限，用网络流（每束容量K）求最大可分配飞机数，装不下的飞机数记为U。保留量S＝clip(ceil(U/K)＋5, 0, 60)。若U＝0，直接用A进入第4步。
2. **以N−S重求骨架。** 预算N−S、间隔规则、原峰值目标，得到布局B。
3. **按需加副本。** 当前站点集合＝B的中心（各带自己的半径上限，按不同站点计算，副本不参与半径计算）。循环：用网络流（每束容量K）分配；若全部飞机都分配了，结束；否则在"合格但未分配飞机最多"的站点加一个副本（同中心、同半径上限、同合格集合，与原束同`stack_id`），束数加一；束数到N仍有未分配飞机就停止，未分配的飞机按原峰值流分给合格束（会超K），记录超K束数。
4. **收窄。** 在每束≤K的约束下做`objective="narrow"`的距离最小指派与重定中心；同一叠放簇内的束共用一个中心，重定中心时整簇一起移动（中心取簇内全部成员的最小包络锥），簇与其它站点之间仍须满足间隔规则，不满足就不移动该簇。
5. **时间。** 单景时间上限改为300秒：第1步与第2步各最多120秒，第3、4步用剩余时间；不再按保留量档位均分。

**验收**：开发集最大场景应用满或接近150束、超K束数为0（或个位数）、叠放簇集中在伦敦等热点；夜间小场景不应产生叠放。
